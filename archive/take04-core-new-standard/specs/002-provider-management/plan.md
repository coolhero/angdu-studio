# Implementation Plan: Provider Management

**Branch**: `002-provider-management` | **Date**: 2026-03-04 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/002-provider-management/spec.md`

## Summary

Provider Management implements the AI provider registry, model catalog, OAuth authentication, and API key configuration that underpin all AI interactions. It builds on F001's IPC bridge, Zustand store infrastructure, and config management to provide: 63 pre-configured system providers across 12 API types, model management with capability detection, 4 OAuth flows (CherryIN PKCE, Copilot device code, Anthropic PKCE, VertexAI service account), CherryAI fallback provider, and provider-specific settings.

## Technical Context

**Language/Version**: TypeScript 5.8
**Primary Dependencies**: Zustand (state), Zod (validation), electron-vite 5, React 19
**Storage**: Zustand persist (localStorage) for providers/models, safeStorage (Copilot token), file-based (Anthropic credentials)
**Testing**: Vitest (unit/integration)
**Target Platform**: Electron 40 (macOS, Windows, Linux)
**Project Type**: Desktop application (Electron)
**Performance Goals**: Provider connectivity test within 5 seconds, store operations < 10ms
**Constraints**: All data stored locally, OAuth tokens secured per provider-specific strategy
**Scale/Scope**: 63 system providers, 12 provider types, ~55 SystemProviderIds, 4 OAuth flows, ~23 IPC channels

## Implementation Phases

### Phase 1: Foundation — Types, Config, Store (US1, US2, US3)

**Goal**: Provider and Model types, system provider configuration, Zustand store with CRUD.

1. Define Provider, Model, ProviderType, SystemProviderId types in `packages/shared/types/provider.ts`
2. Define ProviderApiOptions, LlmSettings, service tier types
3. Create system provider configuration (`src/renderer/src/config/providers.ts`) with 63 providers
4. Create default model configurations (`src/renderer/src/config/models/default.ts`)
5. Create model utility functions (`src/renderer/src/config/models/utils.ts`)
6. Implement `useLlmStore` Zustand store with persist + broadcastSync
7. Implement provider/model hooks (useProvider, useProviders, useSystemProviders, useUserProviders)
8. Add F002 IPC channels to `IpcChannel.ts` enum
9. Create provider preload API (`src/preload/api/provider.ts`)
10. Register provider IPC handlers (`src/main/ipc/provider.ipc.ts`)

### Phase 2: OAuth Services (US4)

**Goal**: All 4 OAuth authentication flows working in main process.

1. Implement CopilotService (device code flow, safeStorage encryption)
2. Implement CherryINOAuthService (PKCE, deep link callback, host allowlisting, token refresh)
3. Implement AnthropicService (PKCE, manual code, file-based credentials, expiry-based refresh)
4. Implement VertexAIService (service account auth, PEM formatting, client caching)
5. Wire OAuth IPC handlers in provider.ipc.ts

### Phase 3: Provider Features (US5, US6, US7, US8)

**Goal**: Provider reordering, settings, CherryAI fallback, default models.

1. Implement provider reordering (moveProvider)
2. Implement provider-specific settings (custom headers, rate limits, API version, apiOptions)
3. Implement CherryAI always-available injection
4. Implement default model selection (4 purposes)
5. Implement URL normalization in selectors
6. Copy provider/model logo assets from original source

### Phase 4: Testing & Polish

**Goal**: Comprehensive test coverage, integration verification.

1. Unit tests for store operations (CRUD, reorder, dedup)
2. Unit tests for hooks and selectors
3. Unit tests for type guards (isSystemProvider, model capability detection)
4. Service tests for OAuth flows (mock HTTP, mock safeStorage)
5. Integration test for persistence (store → localStorage → reload → verify)
6. Demo page: provider list with add/test/configure workflow
