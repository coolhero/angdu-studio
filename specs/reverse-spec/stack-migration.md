## 2. State Management: Redux Toolkit → Zustand

### 2.1 Why Migrate

- Redux Toolkit adds significant boilerplate (slices, reducers, actions, selectors, thunks, store configuration)
- Cherry Studio has ~25 Redux slices with a complex `combineReducers` + `persistReducer` setup
- Cherry Studio's own codebase has marked the Redux store as `@deprecated` and scheduled for removal in v2.0.0
- Zustand is simpler, has a smaller bundle, and integrates naturally with React without providers or connect wrappers

### 2.2 Slice → Store Conversion Pattern

**Redux (Cherry Studio)**:
```typescript
// store/settings.ts
import { createSlice, PayloadAction } from '@reduxjs/toolkit'

interface SettingsState {
  language: string
  theme: ThemeMode
  sendMessageShortcut: SendMessageShortcut
}

const settingsSlice = createSlice({
  name: 'settings',
  initialState: { language: 'en', theme: 'dark', sendMessageShortcut: 'Enter' },
  reducers: {
    setLanguage(state, action: PayloadAction<string>) {
      state.language = action.payload
    },
    setTheme(state, action: PayloadAction<ThemeMode>) {
      state.theme = action.payload
    },
  },
})

export const { setLanguage, setTheme } = settingsSlice.actions
export default settingsSlice.reducer

// Usage in component
const language = useSelector((state: RootState) => state.settings.language)
const dispatch = useDispatch()
dispatch(setLanguage('zh'))
```

**Zustand (Angdu Studio)**:
```typescript
// store/settings.ts
import { create } from 'zustand'
import { persist } from 'zustand/middleware'

interface SettingsState {
  language: string
  theme: ThemeMode
  sendMessageShortcut: SendMessageShortcut
  setLanguage: (language: string) => void
  setTheme: (theme: ThemeMode) => void
}

export const useSettingsStore = create<SettingsState>()(
  persist(
    (set) => ({
      language: 'en',
      theme: 'dark',
      sendMessageShortcut: 'Enter',
      setLanguage: (language) => set({ language }),
      setTheme: (theme) => set({ theme }),
    }),
    { name: 'settings-storage' }
  )
)

// Usage in component
const language = useSettingsStore((s) => s.language)
const setLanguage = useSettingsStore((s) => s.setLanguage)
setLanguage('zh')
```

### 2.3 Thunks → Async Actions

Redux thunks become plain async functions inside the Zustand store or standalone async action functions.

**Redux thunk**:
```typescript
export const sendMessage = createAsyncThunk(
  'messages/send',
  async (payload, { dispatch, getState }) => {
    const state = getState() as RootState
    dispatch(setLoading(true))
    const result = await api.sendMessage(payload)
    dispatch(addMessage(result))
    dispatch(setLoading(false))
  }
)
```

**Zustand equivalent**:
```typescript
export const useMessageStore = create<MessageState>()((set, get) => ({
  loading: false,
  messages: [],
  sendMessage: async (payload) => {
    set({ loading: true })
    const result = await api.sendMessage(payload)
    set((state) => ({
      messages: [...state.messages, result],
      loading: false,
    }))
  },
}))
```

### 2.4 Persistence Strategy

Cherry Studio uses `redux-persist` with `storage` (localStorage) and a custom `migrate` function for schema upgrades.

Zustand equivalent:
- Use `zustand/middleware` `persist` with `localStorage` (or a custom storage adapter for Electron)
- Use the `version` and `migrate` options in `persist()` for schema evolution
- Partialize state to exclude transient/runtime values from persistence

```typescript
persist(
  storeCreator,
  {
    name: 'settings-storage',
    version: 2,
    migrate: (persisted, version) => {
      if (version < 2) {
        // migration logic
      }
      return persisted as SettingsState
    },
    partialize: (state) => ({
      // Only persist these keys, exclude runtime state
      language: state.language,
      theme: state.theme,
    }),
  }
)
```

### 2.5 Store Sync (Main ↔ Renderer)

Cherry Studio has a `StoreSyncService` and `ReduxService` that synchronize Redux state between main and renderer via IPC. In Zustand:

- Use Zustand's `subscribe` to watch for changes and push to main via IPC
- Main process can trigger renderer state updates via IPC events
- Keep the same `IpcChannel` contract for sync messages

## 3. UI Library: Ant Design → shadcn/ui

### 3.1 Why Migrate

- Ant Design is opinionated and heavy (~400KB+ in bundle); shadcn/ui is copy-paste, tree-shakeable, and based on Radix primitives
- styled-components adds a runtime CSS-in-JS overhead; TailwindCSS 4 is compile-time with zero runtime cost
- shadcn/ui components are owned by the project (copied into `components/ui/`), enabling full customization without fighting library internals
- TailwindCSS 4 is a significant upgrade with native CSS support, faster compilation, and better developer experience

### 3.2 Component Mapping Table

| Ant Design Component | shadcn/ui Equivalent | Notes |
|---------------------|---------------------|-------|
| `Button` | `Button` | Variant mapping: primary→default, default→outline, text→ghost, link→link |
| `Input` | `Input` | Direct replacement |
| `Input.TextArea` | `Textarea` | Direct replacement |
| `Input.Search` | `Input` + search icon | Compose with icon |
| `Select` | `Select` | Radix-based, different API surface |
| `Dropdown` | `DropdownMenu` | Uses Radix DropdownMenu |
| `Modal` | `Dialog` | `Modal.confirm` → `AlertDialog` |
| `Drawer` | `Sheet` | Side panel equivalent |
| `Tabs` | `Tabs` | Direct replacement |
| `Switch` | `Switch` | Direct replacement |
| `Checkbox` | `Checkbox` | Direct replacement |
| `Radio` / `Radio.Group` | `RadioGroup` | Direct replacement |
| `Tooltip` | `Tooltip` | Radix-based |
| `Popover` | `Popover` | Radix-based |
| `Table` | `Table` (+ `@tanstack/react-table`) | For complex tables; simple tables use HTML + Tailwind |

### 3.3 Styling Migration: styled-components → TailwindCSS 4

**What changes**:
- Remove `styled-components` dependency and SWC plugin (`@swc/plugin-styled-components`)
- Remove all `styled.*` and `css` template literal usages
- Convert to Tailwind utility classes directly on JSX elements
- For complex/reusable style patterns, use `@apply` in CSS or `cva` (class-variance-authority)

**Migration pattern**:
```typescript
// Before (styled-components)
const Container = styled.div`
  display: flex;
  flex-direction: column;
  padding: 16px;
  background: ${(props) => props.theme.background};
  border-radius: 8px;
`

// After (TailwindCSS)
<div className="flex flex-col p-4 bg-background rounded-lg">
```

**Theme migration**:
- Ant Design's `ConfigProvider` theme tokens → CSS custom properties in `globals.css`
- Cherry Studio uses `ThemeMode` (dark/light/auto) — preserve this with Tailwind's `dark:` variant
- Define color tokens as CSS variables, reference in `tailwind.config.ts`

### 3.4 Icon Migration

Cherry Studio uses `@ant-design/icons` and Lucide React icons. Migration:
- Replace all `@ant-design/icons` with Lucide equivalents
- Keep existing Lucide usage as-is
- Common mappings: `SettingOutlined` → `Settings`, `SearchOutlined` → `Search`, `PlusOutlined` → `Plus`, `DeleteOutlined` → `Trash2`, `EditOutlined` → `Pencil`

### 3.5 Form Handling

- Ant Design's `Form` component with built-in validation → `react-hook-form` + `zod` schemas
- shadcn/ui `Form` component wraps react-hook-form
- Validation rules move from Ant's declarative `rules` prop to zod schemas

## 5. Risks and Mitigations

### 5.1 High Risk

| Risk | Impact | Mitigation |
|------|--------|------------|
| Ant Design component behavior differences | UI regressions, broken interactions | Build a component-by-component checklist. Write Playwright visual regression tests for each migrated screen. |
| Redux-persist → Zustand persist incompatibility | User data loss on upgrade | N/A for Angdu (greenfield). But if importing Cherry data, write a migration adapter. |
| styled-components dynamic theming | Theme-dependent styles may be missed | Audit all `props.theme.*` usages. Map each to a CSS variable. |
| Ant Design's `message` and `notification` imperative APIs | Toast/notification patterns differ | Adopt `sonner` early. Create a `toast()` wrapper that matches the usage patterns. |

### 5.2 Medium Risk

| Risk | Impact | Mitigation |
|------|--------|------------|
| Zustand store granularity | Too many or too few stores | Follow the Redux slice boundaries as a starting point. Merge only when stores are always used together. |
| Ant Design form validation → react-hook-form | Different validation UX | Use zod schemas. Test all form flows with Playwright. |
| TailwindCSS 4 breaking changes from v3 | Docs/examples may reference v3 syntax | Use official TailwindCSS 4 docs. Test with `@tailwindcss/vite` plugin. |
| Loss of Ant Design's built-in accessibility | A11y regressions | Radix primitives (used by shadcn/ui) have strong a11y. But test with screen readers. |

### 5.3 Low Risk

| Risk | Impact | Mitigation |
|------|--------|------------|
| Bundle size increase from duplicated components | Slightly larger bundle | shadcn/ui components are small. Monitor with build analysis. |
| Developer learning curve (Zustand, shadcn/ui) | Slower initial velocity | Both have excellent documentation and simple APIs. |

## 6. Per-Feature Migration Notes

Impact rating reflects how much each feature is affected by the two stack migrations (state management and UI library).

| Feature | State Mgmt Impact | UI Library Impact | Key Migration Notes |
|---------|-------------------|-------------------|---------------------|
| **F001-app-core** | High | High | Window chrome, navigation tabs, sidebar layout, theme system. Foundation for all other features. Migrate first. |
| **F002-providers** | Medium | Medium | Provider list grid, config forms, API key inputs, model capability badges. Settings → Provider uses 3-column Ant layout. |
| **F003-chat** | High | High | Most complex feature. Message list (virtual), input toolbar, streaming display, model selector dropdown. `assistants`, `runtime`, `messageBlock`, `newMessage` slices all involved. |
| **F004-assistants** | Medium | Medium | Assistant CRUD, emoji picker, sidebar list. `assistants` slice → `useAssistantsStore`. |
| **F005-topics** | Medium | Low | Topic list in sidebar, auto-creation from messages. Mostly data logic. |
| **F006-settings** | High | High | Largest settings state (~80 fields). Complex multi-section form. Every Ant component type is used here. |
| **F007-knowledge** | Medium | Medium | Knowledge base list, document upload, embedding progress. `knowledge` slice + IPC-heavy. |
| **F008-translate** | Low | Medium | Split-pane layout, language dropdowns, translate button. Small state surface. |
| **F009-notes** | Low | Low | TipTap editor (no migration), tree sidebar. Minimal Ant usage. |
| **F010-mini-apps** | Low | Medium | Card grid layout, webview embedding. Simple state. |
| **F011-mcp** | Medium | Medium | Server list, config editor (JSON in CodeMirror), marketplace. `mcp` slice. |
| **F012-paintings** | Medium | Medium | Three-panel layout, provider selector, image gallery, prompt input. `paintings` slice. |

### Recommended Migration Order

1. **F001-app-core** — establishes layout system, theme, navigation, and tab management in the new stack
2. **F006-settings** — exercises the full range of form components and the largest Zustand store
3. **F002-providers** — sets up the provider/model infrastructure needed by chat
4. **F004-assistants** — prerequisite for chat
5. **F003-chat** — the core feature, built on top of the foundations
6. **F005-topics** — extends chat with conversation management
7. **F007–F012** — remaining features in any order, as they are more independent
