## 1. Source Code Reference Principles

### New Stack Strategy

Cherry Studio source code is a **logic reference only**. We extract behavioral specifications, data flows, IPC contracts, and business rules — but **not** UI component code or state management patterns.

| Aspect | Reference From Cherry Studio | Rewrite For Angdu Studio |
|--------|------------------------------|--------------------------|
| Business logic | Copy patterns, adapt types | Same logic, new types |
| IPC channels | Keep channel names/contracts | Same IPC layer |
| UI components | Observe behavior only | Rebuild with shadcn/ui + Tailwind |
| State management | Observe shape/flow only | Rebuild with Zustand + electron-store |
| Styling | Ignore entirely | Tailwind utility classes |
| Provider abstraction | Copy provider interface | Same interface, new factory |

**Rule**: Never import or copy-paste Ant Design components, styled-components blocks, or Redux Toolkit slices. Reference the _what_, rewrite the _how_.

## 2. Extracted Architecture Principles

### I. Main/Renderer Process Separation

All code lives in one of two domains:

| Domain | Location | Responsibilities |
|--------|----------|-----------------|
| **Main process** | `src/main/` | OS access, file I/O, native APIs, IPC handlers, background services |
| **Renderer process** | `src/renderer/` | UI rendering, user interaction, store management, API calls to main |

**Rules**:
- Renderer NEVER accesses Node.js APIs directly (no `fs`, `path`, `child_process`).
- Main NEVER manipulates DOM or React state.
- All cross-boundary communication goes through IPC (see Principle II).
- Each process has its own service layer (see Principle III).

### II. IPC-First Communication

All communication between main and renderer processes uses typed IPC channels.

**Observed Pattern** (from `packages/shared/IpcChannel.ts`):
```
enum IpcChannel {
  App_GetCacheSize = 'app:get-cache-size',
  File_Upload = 'file:upload',
  ...
}
```

**Rules**:
- Every IPC channel is declared in a single shared enum (`IpcChannel`).
- Channel names follow `domain:action` format (e.g., `app:info`, `file:upload`, `knowledge:search`).
- Main process registers handlers via `ipcMain.handle(channel, handler)`.
- Renderer invokes via `window.api.*` or `window.electron.ipcRenderer.invoke(channel, ...args)`.
- Streaming responses use `ipcMain.on` / `webContents.send` for push-based patterns.
- No raw string channel names — always use the enum.

### III. Service Layer Pattern

Business logic lives in dedicated service classes, not in UI components or store slices.

**Main process services** (observed 30+ in `src/main/services/`):
- `AppService` — app lifecycle, system info
- `ConfigManager` — persistent configuration
- `FileStorage` — file management
- `KnowledgeService` — RAG/knowledge base
- `MCPService` — Model Context Protocol
- `ProxyManager` — network proxy
- `BackupManager` — data backup/restore
- `ExportService` — data export

**Renderer services** (observed 20+ in `src/renderer/src/services/`):
- `ApiService` — IPC wrapper for main process calls
- `AssistantService` — assistant CRUD
- `ConversationService` — conversation/topic management
- `MessagesService` — message operations
- `ModelService` — model configuration
- `NavigationService` — routing
- `StoreSyncService` — cross-window state sync

**Rules**:
- One service per domain concern.
- Services are singletons (module-level instances or class-based singletons).
- Components call services, not the other way around.
- Services may call other services but avoid circular dependencies.

### IV. Store as Single Source of Truth (Redux → Zustand Migration)

**Cherry Studio Pattern** (Redux Toolkit + redux-persist):
- 25+ store slices combined via `combineReducers`
- Persisted to localStorage via `redux-persist` (key: `cherry-studio`, version: 199)
- Blacklisted slices: `runtime`, `messages`, `messageBlocks`, `tabs`, `toolPermissions`
- Cross-window sync via `StoreSyncService` middleware

**Angdu Studio Target** (Zustand + electron-store):
- Each domain gets its own Zustand store (not one monolithic store)
- Persistence via `electron-store` (main process) instead of `redux-persist` (renderer localStorage)
- Cross-window sync via IPC broadcast (replaces StoreSyncService middleware)

**Rules**:
- UI components read state via Zustand hooks (`useXxxStore`).
- State mutations go through store actions (never direct mutation).
- Transient state (runtime, UI-only) is NOT persisted.
- Persisted state syncs to `electron-store` on the main process via IPC.

### V. Provider Abstraction

AI providers are accessed through a unified interface with provider-specific adapters.

**Observed Pattern**:
- Provider IDs mapped to AI SDK providers via `factory.ts`
- Static mapping: `gemini` → `google`, `azure-openai` → `azure`, `grok` → `xai`, etc.
- Dynamic provider registration via `initializeNewProviders()`
- Provider configuration stored in `llm` store slice

**Rules**:
- All AI interactions go through the provider abstraction layer.
- Adding a new provider = adding config + optional adapter, not changing core logic.
- Provider credentials stored securely (not in Redux/Zustand state, but in electron-store).
- Provider health checks run independently of UI.

## 3. Technical Constraints

### Performance
- Main process must remain responsive — heavy computation offloads to workers or child processes.
- Renderer bundle size monitored — lazy load non-critical pages.
- IPC calls are async — batch where possible, avoid chatty protocols.
- Knowledge base indexing happens in background (main process).

### Security
- **Context isolation**: enabled (`contextIsolation: true`).
- **Node integration**: disabled in renderer (`nodeIntegration: false`).
- **Preload scripts**: bridge between main and renderer — expose only what's needed.
- **CSP**: Content Security Policy enforced — no inline scripts, no `eval()`.
- **API keys**: stored in electron-store (encrypted at rest on supported platforms), never in renderer state.
- **File access**: sandboxed — renderer requests file operations via IPC.

### Compatibility
- **Electron 40**: target Chromium 134+, Node.js 24.x.
- **Platforms**: macOS (arm64, x64), Windows (x64, arm64), Linux (x64, arm64).
- **Node.js**: >=24.11.1 (from `package.json` engines).

## 4. Coding Conventions

### TypeScript
- Strict mode enabled.
- Explicit return types on exported functions.
- Interfaces preferred over type aliases for object shapes.
- Enums for finite sets (e.g., `IpcChannel`, `ThemeMode`).
- `type` imports used where possible (`import type { ... }`).

### File Organization
```
src/
  main/
    index.ts          # Entry point
    ipc.ts            # All IPC handler registrations
    services/         # Business logic services
    utils/            # Shared utilities
    configs/          # Configuration constants
  renderer/
    src/
      App.tsx         # Root component
      Router.tsx      # Route definitions
      pages/          # Page-level components
      components/     # Shared UI components
      services/       # Renderer-side services
      store/          # State management
      hooks/          # Custom React hooks
      types/          # Type definitions
      utils/          # Renderer utilities
      i18n/           # Internationalization
  preload/
    index.ts          # Preload script (IPC bridge)
```

### Naming
- **Files**: PascalCase for components/services (`AppService.ts`), camelCase for utilities (`process.ts`).
- **Components**: PascalCase (`ChatMessage`, `SettingsPage`).
- **Hooks**: `use` prefix, camelCase (`useAppSelector`, `useAssistant`).
- **Store slices/stores**: camelCase (`assistants.ts`, `settings.ts`).
- **IPC channels**: `Domain_Action` enum key, `domain:action` string value.
- **Services**: PascalCase class name + `Service` suffix (`KnowledgeService`, `MCPService`).

## 6. Recommended Development Principles

### Test-First
Write failing tests before implementation. Unit tests for services, integration tests for IPC contracts, component tests for UI behavior.

### Think Before Coding
Read the feature spec fully. Understand data flow end-to-end before writing code. Identify which process (main/renderer) owns each piece.

### Simplicity First
Prefer the simplest solution that satisfies the spec. Avoid premature abstraction. One clear pattern beats three clever ones.

### Surgical Changes
Each commit changes one thing. Each PR addresses one feature or fix. Minimize blast radius.

### Goal-Driven
Every line of code serves a user-visible goal. If you can't trace code back to a feature spec, question its existence.

### Demo-Ready
After each feature, the app should be runnable and demonstrable. No broken intermediate states on main.

## 7. Global Evolution Layer Operational Principles

These principles govern how the codebase evolves over time:

1. **Additive Over Destructive** — Add new capabilities without breaking existing ones. Feature flags over rewrites.
2. **Contract Stability** — IPC channel contracts, store shapes, and service interfaces are public APIs. Changing them requires migration.
3. **Deprecation Path** — Mark deprecated code with `@deprecated` and a removal target version. Never silently remove.
4. **Version Awareness** — Persisted data includes version numbers. Migrations handle schema evolution.
5. **Backward Compatibility** — New versions read data from old versions. Old versions gracefully handle unknown fields.

## 8. Project-Specific Recommended Principles

### AI Desktop App Domain
- **Streaming-First**: AI responses stream by default. UI must handle partial data, cancellation, and error recovery mid-stream.
- **Model Agnosticism**: Never hardcode assumptions about a specific AI provider. The provider abstraction must accommodate any OpenAI-compatible API.
- **Offline Resilience**: The app must function (minus AI features) without network. Local data, settings, and notes must work offline.
- **Token Awareness**: Display token usage, respect context windows, implement conversation pruning strategies.

### Electron Architecture
- **Process Crash Isolation**: Renderer crash must not kill main. Main crash must attempt graceful data save.
- **Memory Budget**: Monitor renderer memory. Large conversations or knowledge bases must paginate/virtualize.
- **Native Feel**: Respect OS conventions — native menus on macOS, system tray behavior, keyboard shortcuts, drag-and-drop.
- **Auto-Update**: Built-in update mechanism with channel support (stable/beta).

### Scale (Medium Complexity, Single-Developer)
- **Feature Isolation**: Each feature should be developable and testable independently.
- **Progressive Enhancement**: Start with core chat, layer features on top. Each layer must not destabilize the base.
- **Dependency Vigilance**: Minimize runtime dependencies. Audit each addition for bundle size and maintenance burden.
- **Documentation as Code**: Specs drive implementation. If the spec doesn't say it, don't build it.
