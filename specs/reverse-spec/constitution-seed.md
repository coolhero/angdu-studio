## 2. Extracted Architecture Principles

These principles are derived from observing Cherry Studio's codebase and represent patterns worth preserving in Angdu Studio.

### 2.1 Singleton Services

Long-lived service instances manage cross-cutting concerns (MCP connections, memory indexing, OCR). Each service owns its lifecycle and exposes a clear API surface.

- Main process: `MCPService`, `MemoryService`, `OcrService`, `KnowledgeService`, `FileStorage`, `ConfigManager`
- Renderer process: `ApiService`, `AssistantService`, `ConversationService`, `MemoryService`, `NavigationService`
- Services are instantiated once and imported as module-level singletons

### 2.2 IPC Bridge Pattern

Main and renderer processes communicate exclusively through typed IPC channels (`ipcMain.handle` / `ipcRenderer.invoke`). All IPC channels are defined in a shared `IpcChannel` enum to ensure type safety across the process boundary.

- Channels are grouped by domain (file operations, provider management, knowledge base, etc.)
- All IPC payloads must be serializable (no functions, class instances, or circular references)
- The preload script exposes a minimal, typed API surface to the renderer

### 2.3 Middleware Pipeline

AI Core uses a request/response transformation pipeline for LLM interactions. Middleware functions compose to handle preprocessing (token estimation, context injection) and postprocessing (streaming, usage tracking).

### 2.4 Registry Pattern

Extensible registries manage pluggable providers: OCR backends, MCP servers, AI model providers, and plugins. New providers are added by registering with the appropriate registry without modifying core logic.

### 2.5 Factory Pattern

Provider factories and importer factories create instances based on configuration. The provider factory resolves the correct SDK adapter (OpenAI, Anthropic, Google, etc.) from a provider type enum.

### 2.6 Dual Database Architecture

- **SQLite (via Drizzle ORM)**: Persistent, structured data — agents, provider configs, knowledge base metadata, settings
- **Dexie (IndexedDB)**: High-frequency, large-volume data — chat messages, conversation history, message blocks
- Rationale: SQLite handles relational queries and persistence; IndexedDB handles the volume and speed requirements of streaming chat data

### 2.7 State Management (Migrating)

Cherry Studio uses Redux Toolkit with ~25 slices, redux-persist for hydration, and a StoreSyncService for main↔renderer state synchronization. Angdu Studio replaces this with Zustand stores while preserving the same domain boundaries and persistence strategy.

## 3. Technical Constraints

### 3.1 Electron Process Model

- **Main process**: Node.js runtime. Handles file system, native APIs, IPC handlers, background services
- **Renderer process**: Chromium runtime. Runs React app, UI rendering, user interaction
- **Preload scripts**: Bridge layer with contextIsolation enabled. Exposes whitelisted IPC methods
- **No direct Node.js access from renderer** — all system operations go through IPC

### 3.2 IPC Serialization

- All data crossing the IPC boundary must be structured-cloneable
- No functions, symbols, or class instances in IPC payloads
- Large binary data (files, images) should use ArrayBuffer or be written to disk with path references
- IPC calls are async — design for latency and error handling

### 3.3 Build System

- **electron-vite** with SWC for fast compilation
- Path aliases configured in `tsconfig.json` and mirrored in vite config (`@renderer`, `@main`, `@shared`, `@types`)
- Separate entry points for main, preload, and renderer

### 3.4 Database Constraints

- SQLite runs in the main process only (no direct renderer access)
- Dexie runs in the renderer process (IndexedDB is browser-native)
- Schema migrations must be forward-compatible and non-destructive
- Drizzle schema changes require migration files

### 3.5 Streaming Requirements

- LLM responses are streamed token-by-token using the Vercel AI SDK
- UI must handle incremental rendering without full re-renders
- Message blocks are appended progressively during streaming
- Abort controllers must be wired for user cancellation

## 4. Coding Conventions

### 4.1 TypeScript

- **Strict mode enabled** (`strict: true` in tsconfig)
- Prefer `interface` for object shapes, `type` for unions and intersections
- No `any` — use `unknown` with type guards when the type is truly dynamic
- Export types separately from values when possible
- Use `as const` for literal enums and configuration objects

### 4.2 React

- **Functional components only** — no class components
- Hooks for all state and side effects
- Custom hooks extract reusable logic (e.g., `useAssistant`, `useModel`, `useTopic`)
- Memoize expensive computations with `useMemo` and callbacks with `useCallback`
- Avoid prop drilling — use Zustand stores or React context for shared state

### 4.3 File Organization

- Feature-based directory structure under `src/renderer/src/`
- Services in `services/`, stores in `store/`, UI components in `components/`
- Pages in `pages/`, organized by route
- Shared types in a top-level `types/` directory
- Constants and configuration in `config/`

### 4.4 Imports

- Use path aliases (`@renderer/`, `@main/`, `@shared/`, `@types`)
- Group imports: external packages, then internal aliases, then relative paths
- Prefer named exports over default exports (except for pages/routes)

### 4.5 Error Handling

- Wrap IPC calls in try/catch with meaningful error messages
- Services should never throw unhandled — catch and log via `LoggerService`
- UI should show user-friendly error states, not raw exceptions
- Use `Result<T, E>` patterns for operations that can fail predictably

### 4.6 Testing

- **Vitest** for unit and integration tests
- **Playwright** for end-to-end tests
- Test files co-located in `__tests__/` directories alongside source
- Mock IPC and services at the boundary, not deep internals

## 6. Recommended Development Principles

### 6.1 Test-First

Write tests before implementation. Each feature starts with failing tests that define the expected behavior. Tests serve as living documentation and prevent regressions.

### 6.2 Think Before Coding

Before writing any code, understand the problem fully. Read the relevant spec, trace the data flow, identify edge cases. A 10-minute analysis prevents a 2-hour refactor.

### 6.3 Simplicity First

Choose the simplest solution that satisfies the requirements. Avoid premature abstraction. Extract patterns only when you see three or more concrete instances.

### 6.4 Surgical Changes

Each commit should do one thing. Each PR should address one concern. Minimize blast radius. If a change touches more than 5 files, question whether it can be decomposed.

### 6.5 Goal-Driven Execution

Every task maps to a feature spec. Work from the spec, not from intuition. If the spec is ambiguous, clarify before implementing. Track progress against the feature checklist.

### 6.6 Demo-Ready Delivery

Every completed feature should be demonstrable. The app should build, launch, and show the feature working. No "it works on my machine" — CI must pass, E2E tests must confirm.

## 7. Global Evolution Layer Operational Principles

These principles govern how the codebase evolves over time:

1. **Additive over destructive**: Prefer adding new code paths over modifying existing stable ones. Use feature flags for gradual rollouts.

2. **Backward-compatible migrations**: Database schema changes must include migration scripts. Never drop columns or tables without a deprecation cycle.

3. **Interface stability**: Public API surfaces (IPC channels, store shapes, service methods) should be versioned. Breaking changes require a major version bump.

4. **Documentation as code**: Type definitions serve as the primary documentation. JSDoc for complex business logic only — do not document the obvious.

5. **Dependency hygiene**: Pin major versions. Review changelogs before upgrading. Audit new dependencies for bundle size, maintenance status, and security.

6. **Performance budgets**: Monitor bundle size, startup time, and memory usage. Set thresholds and fail CI if exceeded.

## 8. Project-Specific Recommended Principles

### 8.1 Domain-Driven: AI Provider Abstraction

The AI provider system is the core domain. All LLM interactions flow through a unified abstraction layer:

- Provider configuration is declarative (type, API key, base URL, models)
- The AI Core middleware pipeline handles request transformation, streaming, and response normalization
- New providers are added by implementing a provider adapter — no core changes required
- Model capabilities (vision, function calling, web search) are declared as metadata, not hardcoded

### 8.2 Architecture-Driven: Dual-Database with IPC Bridge

- SQLite (Drizzle) for structured, relational data accessed via IPC from the main process
- Dexie (IndexedDB) for high-throughput chat data accessed directly in the renderer
- The IPC bridge is the single gateway between processes — never bypass it
- All IPC handlers are registered in a central `ipc.ts` file for discoverability

### 8.3 Scale-Driven: Streaming-First, Virtual Lists

- All LLM interactions use streaming by default — batch mode is the exception
- Long lists (messages, assistants, topics, files) use virtualization to handle thousands of items
- Image generation and knowledge base operations are queued to prevent resource exhaustion
- Background processing (embedding, indexing) runs in workers or the main process, never blocking the UI thread

### 8.4 Quality-Driven: Type Safety, Middleware Composability

- The TypeScript type system is the first line of defense — if it compiles, it should work for common cases
- Middleware functions are pure transformations: `(request) => request` or `(response) => response`
- Shared types between main and renderer live in `@shared/` — never duplicate type definitions
- IPC channel names are defined in a shared enum (`IpcChannel`) to catch mismatches at compile time
- Zustand stores use TypeScript generics for full type inference in selectors and actions
