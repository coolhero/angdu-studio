## 1. Extracted Architecture Principles

### 1.1 IPC-Based Main/Renderer Separation

The application strictly separates concerns between Electron's main process and renderer process:

- **Main process**: Node.js services (file system, database, MCP servers, network requests, system APIs)
- **Renderer process**: React UI, user state, AI SDK streaming, presentation logic
- **Communication**: Typed IPC channels via `IpcChannel` enum — `ipcMain.handle` / `ipcRenderer.invoke`
- **Preload script**: Exposes a narrow `window.api` surface; no direct Node.js access in renderer

**Principle**: All system-level operations route through IPC. The renderer never imports Node.js modules directly.

### 1.2 Service-Oriented Main Process

The main process is organized as singleton services, each responsible for a bounded domain:

| Service | Responsibility |
|---------|---------------|
| WindowService | Window lifecycle (main, mini, selection, trace) |
| FileStorage | File upload/download, path management |
| MCPService | MCP server spawn/connect/disconnect |
| KnowledgeService | Embedding generation, RAG search |
| BackupManager | Backup/restore, export |
| ProxyManager | HTTP/SOCKS proxy configuration |
| ConfigManager | electron-store based configuration |
| AppUpdater | Auto-update lifecycle |
| TrayService | System tray icon and menu |
| ThemeService | Native theme detection and sync |

**Principle**: Each service is a singleton with `getInstance()` pattern. Services communicate via direct method calls within the main process, never via IPC internally.

### 1.3 Centralized Client State (Redux → Zustand)

Cherry Studio uses Redux Toolkit with a single combined store of 26 slices. Angdu Studio migrates to Zustand 5 with independent stores per domain:

- **Persisted stores**: Settings, assistants, LLM config, MCP config, etc. (via `persist` middleware)
- **Ephemeral stores**: Runtime state, active messages, tabs, input tools (no persistence)
- **Multi-window sync**: Custom middleware broadcasts state changes across BrowserWindows via IPC

**Principle**: Each feature owns its store(s). Stores are independent — no combined root. Cross-store reads use `getState()` directly.

### 1.4 Provider Abstraction Pattern

AI provider integration uses a factory pattern through Vercel AI SDK:

- **ProviderFactory**: Maps provider ID → AI SDK provider instance
- **Model configuration**: Provider + model ID + parameters (temperature, maxTokens, etc.)
- **Streaming-first**: All AI interactions use `streamText()` / `streamObject()` from AI SDK
- **20+ providers**: OpenAI, Anthropic, Google, Azure, Bedrock, Ollama, OpenRouter, etc.

**Principle**: Application code never calls provider-specific APIs. All AI interaction goes through the AI SDK abstraction layer.

## 2. Technical Constraints

### 2.1 Electron Security

| Constraint | Implementation | Rationale |
|-----------|---------------|-----------|
| `contextIsolation: true` | Default for all windows | Prevents renderer from accessing Node.js globals |
| `sandbox: false` | Required for preload script functionality | Preload needs some Node.js APIs; tradeoff accepted |
| `webSecurity: false` | Current state in source (should be reviewed) | Allows cross-origin requests; consider tightening |
| `nodeIntegration: false` | Default for all windows except SearchService | Renderer must use IPC, not require() |
| Preload API surface | Narrow typed API via `contextBridge.exposeInMainWorld` | Minimizes attack surface |

### 2.2 Custom Titlebar (Frameless Window)

| Platform | Approach |
|----------|----------|
| macOS | `titleBarStyle: 'hidden'` + `titleBarOverlay` + `trafficLightPosition: { x: 8, y: 13 }` |
| Windows | `frame: false` — custom titlebar with window controls |
| Linux | `frame: false` (default) or `frame: true` if user enables system titlebar |

**CSS constraint**: Top-level drag region uses `-webkit-app-region: drag`. Interactive elements within must use `-webkit-app-region: no-drag`.

### 2.3 Multiple Windows

| Window | Entry Point | Purpose |
|--------|-------------|---------|
| Main | `src/renderer/index.html` | Full application |
| Mini | `src/renderer/miniWindow.html` | Compact quick-chat |
| Selection Toolbar | `src/renderer/selectionToolbar.html` | Text selection floating bar |
| Selection Action | `src/renderer/selectionAction.html` | Selection action handler |
| Trace | `src/renderer/traceWindow.html` | OpenTelemetry trace viewer |

Each window has its own entry point but shares preload script and some state (via StoreSyncService).

### 2.4 Build Configuration

- **electron-vite 5** with rolldown-vite 7 as the underlying bundler
- **Main process**: Single-file output (inlineDynamicImports: true), external Node.js deps
- **Renderer**: Multi-entry (5 HTML files), ESNext target, Tailwind CSS via `@tailwindcss/vite`
- **SWC**: Used via `@vitejs/plugin-react-swc` for fast JSX transforms

## 5. Project-Specific Recommended Principles

### 5.1 Multi-Provider AI

- **Provider-agnostic abstractions**: All AI interaction goes through Vercel AI SDK. Never call provider-specific HTTP endpoints directly.
- **Model-capability awareness**: Some models support vision, function calling, or streaming — the UI must adapt based on model capabilities, not provider name.
- **Graceful degradation**: If a provider is unavailable, show clear error state without breaking the app.

### 5.2 Streaming-First Message Handling

- **Stream by default**: All AI responses use streaming (`streamText`). Batch completion is a fallback.
- **Incremental rendering**: Message UI renders chunks as they arrive. No waiting for complete response.
- **Abort support**: Every streaming request must be cancellable via AbortController.
- **Error mid-stream**: If streaming fails partway, preserve partial response and show error state.

### 5.3 MCP Tool Isolation

- **Process isolation**: MCP servers run as child processes, not in the renderer.
- **Permission gating**: Tool execution requires explicit user permission (auto/manual modes).
- **Tool injection**: MCP tools are injected into AI requests only when enabled — toggled via `mcpEnabled` state.
- **Lifecycle management**: MCP servers are started/stopped independently; crashes don't affect the main app.

### 5.4 Offline-First Data

- **Local storage**: All user data (messages, assistants, settings) stored locally (IndexedDB + localStorage + file system).
- **Cloud sync is opt-in**: WebDAV/S3/Nutstore sync is additive, never required.
- **No server dependency**: The app must be fully functional without internet (except for AI provider API calls).

## 6. Development Principles

### 6.1 TypeScript Strictness

- `strict: true` in all tsconfig files
- No `any` without explicit justification comment
- Prefer `unknown` over `any` for external data
- Use discriminated unions for complex state
- All IPC channel handlers must have typed request/response signatures

### 6.2 Component Design

- Components are pure functions (no class components)
- Props interfaces are explicitly defined (no inline object types for public components)
- Side effects in hooks, not in render
- Prefer composition over prop drilling (use Zustand stores for cross-component state)
- Every page component handles its loading, error, and empty states

### 6.3 Error Handling

- Main process: Errors caught at IPC handler boundary, serialized as Error objects to renderer
- Renderer: React Error Boundary wraps route-level components
- Network errors: Retry logic with exponential backoff for transient failures
- User-facing errors: Toast notifications via Sonner; never raw error messages

### 6.4 Testing Strategy

- **Unit tests**: Vitest for business logic, store logic, utilities
- **Component tests**: @testing-library/react for UI components
- **E2E tests**: Playwright for critical user flows
- **Test file location**: `__tests__/` directories adjacent to source, or `tests/` at root for E2E

### 6.5 Performance

- Lazy-load route pages (React.lazy + Suspense)
- Virtualized lists for large datasets (messages, assistants) via @tanstack/react-virtual
- Debounce expensive operations (search, settings save)
- Avoid re-renders: Zustand selectors with shallow equality comparison

## 7. Global Evolution Layer Operational Principles

### 7.1 Incremental Delivery

- Each Release Group (RG-1 through RG-5) must be independently demoable
- Features within an RG can be partially complete, but must not break previously shipped features
- Every commit should leave the app in a buildable, launchable state

### 7.2 Migration Discipline

- **No hybrid state**: Within a single feature, do not mix old stack (Ant Design, Redux, styled-components) with new stack. Migrate completely or not at all.
- **Feature boundary**: Each feature is migrated as a unit. Cross-feature dependencies use interfaces, not implementations.
- **Type-first migration**: When converting Redux slices to Zustand, define the TypeScript interface first, then implement.

### 7.3 Identity Consistency

- All user-facing strings use "Angdu Studio" (never "Cherry Studio")
- All package scopes use `@angdu/` (never `@cherrystudio/`)
- All persist keys use `angdu-` prefix
- All environment variables use `ANGDU_` prefix for app-specific vars
- Source code comments referencing Cherry Studio should be updated or removed

### 7.4 Dependency Management

- Pin major versions of critical dependencies (Electron, React, AI SDK, TipTap)
- Use workspace protocol (`workspace:*`) for internal packages
- Prefer dependencies already used by Cherry Studio unless the migration explicitly replaces them
- Remove Ant Design, Redux, styled-components, and related packages once migration is complete per feature
