**Input context required**:

**Rules**:
1. Follow plan step order strictly.
2. After each step, the app must build without errors.
3. Use shadcn/ui components — install via `npx shadcn@latest add <component>` if not yet added.
4. Use Zustand stores — follow the pattern in `stack-migration.md`.
5. IPC handlers go in `src/main/ipc.ts`; service logic in `src/main/services/`.
6. Renderer services in `src/renderer/src/services/`.
7. All strings user-facing must use i18n (`useTranslation` hook).
8. Apply naming conventions from constitution (Angdu, not Cherry).
9. Write tests alongside implementation (test file co-located or in `__tests__/`).

## Cross-Feature Awareness Rules

### Dependency Enforcement
- A feature MUST NOT be implemented before its dependencies are verified.
- Dependency chain: F01 → F03, F04; F02 → F04, F11, F12; F01+F02 → F07, F08, F09; F05 → F06.
- F01 (Chat Core) and F02 (Provider Management) have no dependencies — start here.

### Shared Infrastructure
These are built as part of T1 features and shared by all:

| Infrastructure | Built By | Used By |
|---------------|----------|---------|
| IPC channel enum | F01 | All |
| Zustand persist adapter (electron-store) | F01 | All persisted stores |
| Provider abstraction | F02 | F01, F04, F07, F09, F11, F12 |
| Theme system (Tailwind + CSS vars) | F05 | All |
| i18n setup | F01 | All |
| Layout shell (sidebar + content) | F01 | F03, F04, F05, F07, F10 |

### Naming Consistency
- All features use `Angdu` branding (never Cherry).
- Store persist keys use `angdu-studio` prefix.
- IPC channels keep `domain:action` format from Cherry Studio (the domain names are generic, not branded).

### State Boundaries
- Each feature owns its Zustand store. No store reads another store directly.
- Cross-feature communication uses: (a) IPC events, (b) React context, or (c) service layer calls.
- Exception: `useSettingsStore` is read-only for other features (theme, language, paths).

### Testing Boundaries
- Unit tests: per-service, per-store. Mock IPC calls.
- Component tests: per-page. Use Testing Library.
- E2E tests: per user-flow. Use Playwright with Electron support.
- Each feature must have at least: 1 store test, 1 service test, 1 component test.
